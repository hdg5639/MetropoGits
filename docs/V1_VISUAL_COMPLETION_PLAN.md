# v1 시각 완성 로드맵

작성일: 2026-10-18

상태: VIS-00~02 완료; 다음 작업은 VIS-06 통제 비교 및 도로·아키타입 가독성 보완

대상: v1 후보의 도시 표현력, 쇼케이스 품질, 교차 저장소 검증

## 1. 목적

MetropoGits의 분석 결과를 삭제하거나 과장하지 않으면서, 처음 보는 개발자가 도시만 보고 주요 서비스 경계와 구조를 이해할 수 있는 v1 시각 결과를 만든다.

분석 정확도와 시각적 완성도는 서로 독립된 목표로 관리한다.

- **분석 정확도:** 모든 의미, 건물, 관계가 소스 근거로 역추적되어야 한다.
- **도시 표현력:** 같은 분석 결과를 화면 목적과 확대 수준에 맞게 읽기 쉬운 도시로 보여야 한다.
- **배포 품질:** 작은 README 이미지와 대형 WebGL 탐색기 모두에서 동일한 도시로 인식되어야 한다.

공개 저장소 전환은 사용자가 2026-10-18 완료했다. GitHub API에서도 public 상태를 확인했다. GitHub Pages는 아직 활성화되지 않았으며 별도 배포 결정 전까지 보류한다.

## 2. 현재 기준선

### GamjaOJ

- 681 buildings
- 117 districts
- 31 networks
- 밀집된 블록형 도시로 표현됨
- 블록 중첩 수정 후 주요 구역의 공간 분리가 유지됨

### GamjaBox

- 1,324 buildings
- 506 districts
- 135 networks
- 여러 서비스 구역이 연결된 대규모 복합도시로 표현됨
- 비직사각형 블록과 Semantic LOD로 이전의 넓은 공터 문제를 줄임

두 저장소가 서로 다른 형태의 도시를 만든다는 점은 확인했다. 다만 두 저장소 모두 Java 중심 성격이 강하므로, 이것만으로 레이아웃 일반화나 의미 분석의 과적합 해소를 확정하지 않는다.

## 3. 외부 피드백 판정

| 피드백 | 판정 | 현재 구현과 후속 조치 |
| --- | --- | --- |

| 도로가 선처럼 보여 회로기판에 가까움 | **시각적 문제 확인** | 도로 폭, 노면, 갓길, 계층별 거리 예약과 최단경로 라우팅은 이미 있다. 신규 도로 시스템보다 기존 구조 도로와 증거 관계 도로의 시각적 위계를 강화한다. |

| GamjaBox가 세로로 길어 16:9에서 작게 보임 | **확인됨** | canonical 도시 좌표를 스크린샷 때문에 왜곡하지 않는다. 먼저 쇼케이스 전용 투영, 결정론적 회전, 자동 프레이밍과 크롭으로 해결한다. |
| 건축 아키타입을 더 구체화해야 함 | **부분 구현됨** | Gate, Service Office, Warehouse, Depot, Cache Tower, Exchange, Port, Control Center, Library 계열이 이미 있다. 새 종류를 무작정 늘리기보다 원경에서도 식별되는 실루엣과 범례를 강화한다. |
| 주요 구역의 정체성이 더 필요함 | **부분 구현됨** | 근거 기반 주요 구역과 라벨은 존재한다. 중복된 짧은 라벨을 경로 문맥으로 구분하고 대표 시설의 존재감을 높인다. |
| Street-Level LOD가 필요함 | **부분 구현됨** | Overview, District, Detail 3단계가 이미 있다. 단계별 대표 건물·도로 선택과 전환을 다듬고 정적 쇼케이스에도 같은 원칙을 적용한다. |
| 동일한 시점·스케일에서 두 WebGL 도시를 비교해야 함 | **미검증, 타당함** | 같은 yaw/pitch, 같은 뷰포트 점유율, 같은 LOD 조건의 비교 캡처와 조작 성능 기준선을 추가한다. |

## 4. 우선 작업 순서

각 항목은 독립된 작업 단위와 커밋으로 완료한다.

### VIS-00. 문서 기준선 정합화

상태: 완료. [현재 계약](contracts/CURRENT_BASELINE.md), README, v1 후보 상태와 ADR-007을 정합화했다. 회귀 테스트는 218개 실행, 217개 통과, Windows symlink 1개 skip이다.

- README의 v1 승격 조건 개수와 실제 조건을 일치시킨다.
- `V1_CANDIDATE.md`의 테스트 수를 현재 검증 결과로 갱신한다.
- 기반 기술 문서의 City 계약 버전과 ADR-009의 `city/0.2`를 일치시킨다.
- v1 기능 범위와 P2 기능을 다시 분리해, 이미 구현된 P2 기능의 추가 확장을 중단한다.

완료 기준:

- README, v1 후보 문서, 기술 명세, ADR 사이에 현재 계약과 승격 조건의 모순이 없다.

### VIS-01. README Showcase 출력 계약 결정

상태: [ADR-013](adr/ADR-013.md)로 구현 계약 확정; VIS-02에서 구현 및 검증 완료.

- 상세 탐색용 `preview.svg`와 README 전시용 결과의 책임을 분리하는 ADR을 작성한다.
- 권장안은 기존 `preview.svg` 호환성을 유지하고 `showcase.svg`를 추가하는 것이다.
- 두 출력은 같은 `city.json`을 사용하며, 쇼케이스가 존재하지 않는 건물이나 관계를 만들지 못하게 한다.
- 쇼케이스 요소가 어떤 district, building, network를 대표하는지 추적 정보를 유지한다.

완료 기준:

- 출력 파일, CLI 동작, Action 연동, 호환성, 추적성 규칙이 ADR로 확정된다.

### VIS-02. 결정론적 Showcase Renderer 구현

상태: 완료. `build`에 `showcase.svg`와 manifest checksum을 추가하고 README 스니펫을 연결했다. CPU/WebGL 블록·형태 비교, 실제 두 저장소와 Spring/구조 전용 fixture의 SVG 검사, 반복 생성 검증을 수행했다. 자세한 사용법은 [SHOWCASE.md](SHOWCASE.md), 관측 결과와 남은 한계는 QUALITY_LOG를 참고한다.

- 주요 서비스 구역과 의미 있는 대표 시설을 우선 표시한다.
- Overview와 동일한 블록 대표물을 사용하되 너무 적은 건물만 남지 않도록 밀도 하한을 둔다.
- 구역 간 관계는 중요도와 근거 수에 따라 제한하고, 세부 참조선은 숨긴다.
- 16:9 프레임 점유율을 최대화하도록 자동 fit과 여백을 계산한다.
- 작은 Spring fixture의 기존 상세 SVG에서 상위 구역 면이 제목 영역을 가리는 문제가 확인됐다. 투영 경계는 모든 표시 면을 포함하고, 제목/범례 영역을 보호하도록 상세 preview와 showcase 모두 회귀 검증한다.
- 필요하면 canonical 좌표는 유지한 채 출력 투영만 결정론적으로 90도 회전한다.
- 상세 SVG와 WebGL의 구역 배치 및 랜드마크 위치가 같은 도시로 인식되어야 한다.

완료 기준:

- 동일 입력을 두 번 생성했을 때 바이트 또는 canonical geometry가 동일하다.
- GamjaOJ와 GamjaBox 모두 16:9 썸네일에서 주요 구역과 대표 시설을 식별할 수 있다.
- 숨기거나 집계한 모든 요소를 원본 City 요소로 역추적할 수 있다.

### VIS-03. 도로 가독성 강화

- 새 관계를 만들지 않고 기존 구조 도로와 증거 기반 관계 도로를 명확히 구분한다.
- 대로, 일반 거리, 골목의 노면 폭·명도·연석 차이를 원경에서도 보이게 한다.
- HTTP, messaging, dependency route는 노면 전체가 아니라 도로 위 표식 또는 제한된 강조로 표현한다.
- 교차로, 횡단 공간, 작은 광장은 구조 도로에서 결정론적으로 파생하고 비의미 시각 요소임을 명시한다.
- 건물 위를 통과하는 관계 도로 비율을 계속 0으로 유지한다.

완료 기준:

- README 크기에서 블록 사이의 거리와 관계 연결을 서로 다른 것으로 읽을 수 있다.
- 범례와 Inspector가 구조 도로를 실제 소스 관계로 오인시키지 않는다.

### VIS-04. 기존 아키타입의 원경 식별력 강화

- 이미 존재하는 아키타입 계열의 실루엣, 지붕, 비율 차이를 확대한다.
- 기술 하나마다 전용 모델을 추가하지 않는다.
- technology, capability, role, urban archetype의 매핑 손실을 집계해 generic 비율의 원인을 구분한다.
- 색만으로 의미를 구분하지 않도록 형태와 범례를 함께 개선한다.

완료 기준:

- Service, Entry Point, Persistence, Cache, Port/Exchange, Test 계열 중 주요 시설을 색을 제외해도 구분할 수 있다.
- 각 형태는 직접 근거 또는 문서화된 파생 규칙을 가진다.

### VIS-05. 구역 정체성과 라벨 정리

- `tests`처럼 서로 다른 경로가 같은 짧은 이름을 갖는 경우 문맥 라벨을 사용한다.
- Auth, VM, Ops, Portal과 같은 주요 경계가 첫 화면에서 겹치지 않고 식별되게 한다.
- 대표 시설은 분석 근거가 있는 경우에만 랜드마크로 강조한다.
- 라벨 수를 확대 수준에 따라 제한하고 충돌 회피를 적용한다.

완료 기준:

- 같은 화면의 주요 구역 라벨이 모호하거나 중복되지 않는다.
- 라벨과 랜드마크는 실제 경로 및 소스 근거로 연결된다.

### VIS-06. 통제된 교차 저장소 비교와 성능 기준선

- GamjaOJ와 GamjaBox를 같은 viewport, yaw, pitch, LOD 정책으로 캡처한다.
- 절대 월드 스케일 비교와 화면 점유율 정규화 비교를 구분한다.
- 초기 렌더 시간, 회전·줌 입력 반응, 대표 FPS 또는 프레임 시간의 기준선을 기록한다.
- Overview, District, Detail 각각에서 표시 건물·도로 수와 시각 문제를 기록한다.

완료 기준:

- 두 저장소의 차이가 카메라 우연이 아니라 데이터와 레이아웃 차이임을 설명할 수 있다.
- 대형 저장소의 탐색 성능 저하가 수치로 기록되고 재현 가능하다.

### VIS-07. 기존 JS/TS 의미 분류의 적용 범위와 오탐 검증

- `app/**/page.tsx`, `app/**/route.ts`와 테스트 소스 규칙은 이미 catalog 0.4.0에 구현되어 있다. [PATH 규칙](PATH_SEMANTICS.md)과 양성·음성 fixture를 현재 기준선으로 사용한다.
- Java 중심 두 저장소 외에도 작은 비 Java 저장소에서 적용 범위와 near-match 오탐을 검증한다.
- 새 경로 규칙이 필요하다는 실제 사례가 확인되면 양성·음성 fixture와 함께 추가한다.
- generic 감소가 실제 증거 증가 때문인지 검증한다.

완료 기준:

- portal 계열의 대표 시설이 실제 파일 경로와 규칙으로 설명된다.
- 오탐과 미탐 사례가 fixture 및 golden 결과로 고정된다.

## 5. 별도 승인 게이트

### 파일 크기 메트릭

`lineCount`와 `byteSize`를 UCG FILE 엔티티에 추가하는 작업은 스카이라인 다양성에 도움이 될 수 있다. 그러나 공개 UCG 계약 변경이므로 별도 ADR과 사용자 승인이 필요하다.

승인 전에는 다음을 하지 않는다.

- UCG 또는 City 공개 스키마에 크기 필드를 임의 추가
- 파일 크기만으로 건물 역할이나 중요도를 주장
- 코드 크기가 아키타입 의미보다 우선하는 스카이라인 생성

승인 후에도 로그 스케일과 상한을 사용하고, 역할 기반 아키타입 실루엣을 우선한다.

## 6. 공통 검증 기준

시각 작업은 다음 조건을 모두 확인한다.

- 실제 저장소 코드를 실행하거나 의존성을 설치하지 않는다.
- 같은 입력과 버전에서 결과가 결정론적으로 재생성된다.
- 모든 의미 건물과 관계 도로는 소스 근거로 역추적된다.
- 집계 시설은 실제 코드 요소가 아님을 UI와 Inspector에서 명시한다.
- 주요 구역 및 시각 블록 사이에 겹침이 없다.
- 관계 도로가 건물 면적을 관통하지 않는다.
- 추가·삭제가 없는 형제 요소의 위치 churn을 측정한다.
- 16:9 README 크기에서 화면 점유율, 라벨 충돌, 도로 가독성을 검사한다.
- WebGL과 정적 출력이 동일한 `city.json`의 같은 도시로 인식된다.
- 작은/중간/대형 및 의미 정보가 적은 fixture를 주기적으로 비교한다.

## 7. 하지 않을 작업

- 이미 공개된 저장소의 상태를 유지하며, Pages 배포는 사용자 승인 없이 진행하지 않는다.
- history replay, metropolis, synthetic activity 등 P2 기능을 더 확장하지 않는다.
- 스크린샷을 예쁘게 만들기 위해 canonical 도시 좌표를 임의 왜곡하지 않는다.
- 나무나 가로등 같은 장식으로 구조적 공백이나 잘못된 레이아웃을 가리지 않는다.
- 라이브러리별 일회성 건물 모델로 카탈로그를 과적합하지 않는다.
- 근거가 없는 서비스 이름, 통신 관계, 트래픽을 생성하지 않는다.
