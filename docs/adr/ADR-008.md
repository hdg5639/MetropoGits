# ADR-008: Occupancy-derived district territory

- Status: Accepted
- Date: 2026-10-17
- Decision owners: Project maintainer
- Applies to: district rendering in the WebGL, 2D, and CPU SVG views

## Context

The canonical `city/0.1` district geometry uses nested axis-aligned rectangles.
Those rectangles are useful allocation bounds: they make containment,
collision checks, deterministic hints, and small-change stability tractable.
They are a poor visual boundary for irregular directory trees, however. A
district with several differently shaped child subtrees paints its complete
bounding box as land, including large areas that contain no code buildings.
On the 1,324-building GJ-Cloud reference repository this makes VM and Ops look
like sparse rectangular fields even after compact sibling packing.

Replacing the allocator, containment validator, and hint contract with
arbitrary polygons in one migration would weaken the existing stability gates.
Keeping the rectangles as the visible land would preserve an implementation
detail at the expense of the intended city metaphor.

## Decision

Separate the stable allocation envelope from the rendered district territory.

- `district.x`, `z`, `width`, and `depth` remain the canonical allocation and
  containment bounds in `city/0.1`.
- Static packaging derives a deterministic orthogonal territory mask from the
  real building footprints in each district subtree. No source fact, entity,
  role, relationship, or canonical coordinate is added or changed.
- Occupied blocks are quantized onto a fixed world grid and disconnected blocks
  are joined by deterministic shortest orthogonal corridors. The union is
  emitted as merged rectangles plus exterior boundary segments, allowing holes
  and concave outlines without a browser triangulation dependency.
- WebGL, the 2D fallback, and the CPU SVG preview consume the same derived
  territory data. Camera fitting uses occupied territory and evidenced network
  paths rather than unused rectangular allocation corners.
- Territory is explicitly a visual projection. Selection and inspector labels
  still resolve to the canonical district ID, while buildings and roads retain
  their existing evidence links.
- A district with no descendant buildings falls back to its canonical bounds,
  so empty and unsupported structural input continues to degrade gracefully.

This decision is additive and does not revise the City Scene schema. A future
shape-aware allocator may let sibling allocation envelopes interlock, but that
would require a separately reviewed layout version, polygon collision rules,
hint migration tests, and an updated geometric validator.

## Determinism and safety rules

- Grid size, block margin, traversal order, neighbor order, and tie-breaking
  are constants covered by fixtures.
- Inputs are only validated City Scene geometry; repository source is not read
  or executed by the territory builder.
- Territory rectangles stay inside their canonical district bounds.
- Every descendant building intersects its ancestor territories.
- Repeated inputs must produce byte-identical viewer data and SVG output.

## Alternatives considered

### Render canonical rectangles unchanged

Rejected because the visible empty land is an allocator artifact, not a fact
about the repository, and dominates large-city composition.

### Replace canonical bounds with arbitrary polygons immediately

Deferred because it changes containment, overlap validation, hint migration,
network routing, and small-change guarantees at once. Visual territory provides
the irregular city boundary without discarding those audited invariants.

### Use a convex hull around buildings

Rejected because a convex hull still fills the large internal and edge voids
that motivated the change.

### Use random or force-directed organic outlines

Rejected because they are harder to reproduce, can imply graph communities as
geography, and are not required to express an irregular occupied footprint.

## Consequences

- Districts can appear concave and may contain unpainted courtyards while their
  canonical allocation remains rectangular and stable.
- Generated viewer data grows by a bounded amount proportional to occupied
  territory cells rather than repository source size.
- The renderer must treat a district as a union of rectangles for drawing and
  hit testing.
- This change corrects false-looking land coverage but does not yet relocate
  buildings into gaps. Remaining spatial waste must be measured after visual
  inspection before considering a polygon-aware allocator migration.
