# ADR-012: Traceable block aggregates for overview LOD

- Status: Accepted
- Date: 2026-10-18
- Decision owners: Project maintainer
- Applies to: large-city overview rendering and aggregate inspection

## Context

The first semantic LOD replaces every building below one major service district
with a single aggregate facility. This keeps large repositories interactive,
but reduces the 1,324-file GJ-Cloud city to seven isolated structures. The
service territory remains full size, so the overview reads as empty land with
one tower rather than as blocks and streets.

Layout 1.13 already gives nearby small leaf districts compact, deterministic
geometry. The overview should preserve that urban grain without rendering
every file building. Any overview structure must remain visibly nonsemantic
and traceable to the canonical files and districts that it represents.

## Decision

Replace service-wide aggregate facilities with deterministic block aggregates.

- Each building is assigned to a major district through its real district
  ancestry. Buildings inside that boundary are partitioned in stable spatial
  order, and the lowest common canonical district is retained as each block's
  owning district.
- The target block population is derived from total city size. Large cities
  aim for roughly the square root of their building count, bounded to 12-48
  overview blocks, so detail increases without returning to file-level noise.
- A block's footprint is derived from the occupied bounds of its canonical
  member buildings and clipped to its major district's polygon territory. It does not
  claim that the enclosing shape is a source-level module or service. When a
  selected major district is nested inside a residual parent group, its
  territory is subtracted from the parent's visual blocks so the two overview
  layers cannot paint the same land.
- A block renders a bounded square-root sample of representative masses, up to
  16. Plot selection balances separation with the block center, and incomplete
  rows are centered, so deterministic tie-breaking cannot repeatedly bias
  overview structures toward the upper-left corner.
- Every block stores sorted, unique `memberEntityIds` and
  `memberDistrictIds`. The inspector discloses the visual-only nature of the
  block, lists its composition, and allows the user to enter the real
  constituent buildings.
- Overview filters hide blocks with no matching member. They do not rewrite a
  block's population or invent a filtered semantic aggregate.
- District and detail LOD continue to render real file buildings. Selecting a
  block while changing LOD may keep that block visible until selection is
  cleared, preserving inspection continuity.

## Data and evidence boundaries

- Block aggregates exist only in packaged viewer projection code. They are not
  UCG entities, City Scene buildings, inferred services, or evidence records.
- City Scene remains `city/0.2`; UCG, stable IDs, network edge IDs, and layout
  coordinates are unchanged.
- Aggregate IDs are deterministic presentation IDs and must use the
  `visual:block:` namespace.
- A block may summarize several canonical districts, but every member district
  and file remains independently selectable after entering detail view.

## Stability and compatibility

- Fixed viewer input must produce byte-identical block IDs, membership,
  geometry, part allocation, and visibility.
- Every large-city building must belong to exactly one overview block.
- Block footprints must remain within their owning major district and may not
  overlap another block footprint.
- Small cities continue directly to detail view and need no overview blocks.

## Required measurements

Quality checkpoints record:

- overview block count and files-per-block distribution;
- complete and unique file membership;
- block-footprint containment and overlap count;
- visible overview mass compared with the former service-wide facilities;
- deterministic output and full viewer/end-to-end regression results.

## Alternatives considered

### Keep one landmark per service

Rejected because it erases the existing internal blocks and leaves most of a
large service territory visually empty.

### Show a fixed percentage of file buildings

Rejected because sampling creates scattered dots, gives weak spatial context,
and does not communicate that omitted files still occupy the district.

### Add aggregate buildings to City Scene

Rejected because an overview block is a renderer projection, not a repository
fact. Encoding it as a canonical building would mix visualization with
evidence-backed analysis.

### Rasterize each major district into an arbitrary uniform grid

Rejected because grid cells can cut meaningful directory groups without using
the hierarchy and compact geometry already produced by layout 1.13.

## Consequences

- Metropolitan view shows a service as a campus of several blocks rather than
  one tower in a field.
- Block count varies with repository size and hierarchy, so overview density is
  comparable across small and large services without a project-specific rule.
- Some blocks summarize multiple small sibling districts. Their inspector must
  therefore present all represented districts instead of implying that the
  block is identical to its owning district.
