# ADR-014: Evidence-aware frontage inside directory-owned geography

- Status: Accepted for implementation
- Date: 2026-10-18
- Authority: maintainer approval in the development conversation
- Supersedes: ADR-004's blanket exclusion of relationships from coordinates;
  narrows DEC-007 to preserve directory ownership rather than hash-only placement

## Decision

Keep every directory, parent relation and file owner. Within that hierarchy,
use evidenced roles and static file relationships to choose frontage and nearby
sites. This is not global graph-community layout or a runtime service-flow map.

- Entry points and evidenced external adapters prefer a local boundary.
- Files referenced from outside their directory have a bounded frontage bias.
  A Service name alone is not evidence. Persistence roles prefer sheltered
  sites unless actual cross-boundary references argue otherwise.
- Only DIRECT/RESOLVED, evidenced file-to-file dependencies influence proximity.
  Deduplicate pairs and normalize popular targets so shared utilities do not
  pull every building into one hub. CONTAINS/DECLARES and package declarations
  do not imply a service call. Roles must carry evidence as well.
- Use stable, bounded local assignment rather than an unconstrained force
  simulation. Unknown files retain a structural fallback. Ties use stable IDs.
- Pack internally oriented child groups before frontage groups, while retaining
  compactness as a constraint. Related sibling groups may influence placement
  only within their common parent. Never move a file across its owner boundary.
- Reserve circulation before placing buildings: blocks of at most three rows
  or columns are separated by an allocation-cell-wide street. Narrow seams
  within blocks are access paths, not new logical relationships.
- Derive street surfaces from available land and retain evidence routes with
  exact original edge membership. Roads must not intersect file footprints.
  Overview must show circulation between representative masses, not an opaque
  podium hiding the street network. Aggregates remain explicitly visual.

## Compatibility and stability

New canonical placement uses `hierarchical-paged/1.14`; UCG `ucg/0.1` and City
`city/0.2` fields and IDs are unchanged. Old scenes remain readable. Old layout
hints are rejected with diagnostics because circulation spacing changed.
Compatible hints lock existing positions before optimizing new items; a new
dependency must not silently rearrange an otherwise unchanged hinted city.
Cold layouts may change when evidence changes. Record that limit explicitly.

The first implementation is a bounded directory-local heuristic, not a promise
that every gate is on the outer edge of its major service district. A deeply
nested or single-file directory may have no alternative site. Do not violate
containment or fabricate service boundaries to satisfy a visual preference.

## Verification

Test deterministic permutation invariance, role/evidence negatives, boundary
versus interior assignment, normalized relation attraction, hint preservation,
containment, overlap and road/building intersections. Inspect both GJ-Cloud and
GamjaOJ plus small/unknown fixtures. Record layout density, relation distance,
frontage distance and algorithm-migration churn separately from small-change
churn. Compare the same canonical scene in SVG and WebGL.

Cache rendering and legend fixes remain separate work units; they do not
authorize changes to graph facts. No HTTP or messaging network may be inferred
merely from an import, filename, placement, or a visual street.
